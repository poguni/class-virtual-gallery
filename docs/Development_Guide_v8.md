## 2. 목표 및 배경

- 미술 시간에 완성한 작품을 교실 벽에만 걸어두지 않고, **언제 어디서나 들어가 볼 수 있는 전시관**으로 만들어 주기 위해 시작했습니다.
- 교사는 사진 파일을 한 번에 올리기만 하면 되고(파일명으로 이름·제목 자동 입력, 전시실 자동 배정), 학생·학부모는 **QR코드 하나로** 바로 입장합니다.
- 감상 활동(좋아요·댓글)을 교사가 **감상 결과 리포트**로 내려받아 평가 자료로 활용할 수 있습니다.
- Phase 7에서는 실제로 여러 선생님이 쓰게 되면서 **보안(아무나 데이터를 지울 수 있던 문제)**과 **교사별 전시 분리**가 핵심 목표가 되었습니다.

## 3. 주요 기능

**감상(학생·학부모)**
- 로그인 없이 입장, QR코드·공유 링크(`?t=교사코드`)로 해당 교사의 현재 전시 관람
- 1인칭 이동: PC는 WASD + 방향키 + 마우스 클릭, 모바일은 자체 구현 조이스틱 + 드래그 + 탭
- 로비 → A동 전시실들 → 연결 통로 → B동 전시실들 → 로비로 돌아오는 순환(ㅁ자) 동선
- 작품 확대 보기, 좋아요(방문자 키로 중복 방지), 댓글(이름 10자·내용 80자)
- 스마트폰 뒤로 가기 시 열린 창만 한 단계씩 닫힘

**관리(교사)**
- 회원가입 → **관리자 승인** 후 사용 (Phase 7)
- 새 전시 만들기: 폴더/여러 장 업로드, 파일명(`번호_이름_제목.jpg`) 자동 해석, 방 자동 배정(방당 8점 기준 균등 분배), 진열 순서(이름순·랜덤·직접)
- 기존 전시 관리: 정보 수정, 작품 수정·삭제·순서 변경, 작품 추가, 전시 삭제
- **현재 전시장 설정**: 교사마다 하나의 전시를 방문자에게 공개 (Phase 7에서 `is_active` 방식으로 재구현)
- 댓글 숨김/복원, 감상 결과 리포트(오프라인 HTML 파일) 다운로드
- 관리자 전용 **교사 승인 탭** (Phase 7)
- 시작 화면·전시장 안 로그아웃 버튼

## 4. 기술 스택 및 아키텍처

### 4.1 구성 요소

| 영역 | 사용 기술 | 선택 이유 |

| 화면·3D | Vanilla JS + Three.js r128 (cdnjs) | 빌드 없이 파일만 올리면 동작, 교사가 직접 관리하기 쉬움 |

### 4.2 파일 구조 (Phase 7에서 분리)

```
(저장소 루트)
├── index.html              ← 화면 구조(HTML)만. CSS·JS를 불러옴
├── css/style.css           ← 모든 화면 디자인
├── js/                     ← 아래 순서대로 불러옴 (순서 변경 금지)
│   ├── auth.js             ← Supabase 연결, 로그인, 교사 승인 확인, QR코드
│   ├── demo-data.js        ← 데모(더미) 작품
│   ├── gallery-data.js     ← 전시·좋아요·댓글 불러오기
│   ├── scene.js            ← 3D 전시장 (로비·복도·전시실·조명·작품 배치)
│   ├── controls.js         ← 이동, 벽 충돌, 모바일 조이스틱
│   ├── viewer.js           ← 화면 갱신 루프, 시작 화면, 작품 창, 좋아요·댓글
│   ├── admin-upload.js     ← 새 전시 만들기, 교사 승인 탭
│   ├── admin-manage.js     ← 기존 전시 관리, 기존 전시에 작품 추가
│   └── report.js           ← 감상 결과 리포트
├── assets/                 ← 시작·로그인 화면 배경 (PC/모바일)
├── supabase/
│   ├── migrations/         ← 적용한 DB 변경 SQL (기록용)
│   └── rollback/           ← 되돌리기 SQL
├── docs/                   ← 개발 가이드(이 문서)
└── README.md               ← 배포 가이드
```

- JS 파일은 모듈(`import`)이 아닌 **일반 `<script>`**로 불러와 전역 변수를 함께 씁니다. 앞 파일의 변수·함수를 뒤 파일이 사용하므로 `index.html`의 불러오는 순서를 바꾸면 안 됩니다.
- `index.html`의 `css/style.css?v=20261024`, `js/*.js?v=20261024`의 `?v=`는 **브라우저 캐시 방지용**입니다. CSS/JS를 고쳐 배포할 때마다 날짜를 새로 바꿉니다.

## 6. 전체 공간(동선) 구조

```
                 ┌───────────────┐
                 │     로비      │  (환영 사인: 실제 전시 학년/반 표시)
                 │  A동문   B동문 │
                 └──┬─────────┬──┘
                    │         │
              [A동 복도]   [B동 복도]
                    │         │
              [제1전시실]  [제N전시실]  (B동은 방 번호를 뒤집어서 지음)
                    │         │
                    …         …
                    │         │
              [제k전시실]  [제k+1전시실]
                    │         │
                    └────┬────┘
                   [연결 통로(가로)]  ← 두 동의 가장 안쪽 끝을 이어붙임
```

- 전시실의 앞쪽 절반은 A동(나가는 길), 뒤쪽 절반은 B동(돌아오는 길)에 배정합니다. B동은 방 순서를 뒤집어 지어서, 연결 통로를 지나 로비 쪽으로 걸어오면 번호 순서대로 마주칩니다.
- 두 동의 깊이가 다르면 얕은 쪽을 곧은 복도로 이어 붙여 맞춘 뒤 연결 통로로 잇습니다.
- 전시실이 1개뿐이면 B동은 통로만 있는 짧은 복도가 되지만 순환 구조는 유지됩니다.
- 예: 작품 22점 → 방 3개(8/7/7) → A동에 1·2관, B동에 3관. 2관 → 연결 통로 → 3관 순서로 지나갑니다.

## 7. 코드 구조 — 파일별 핵심 함수·상수 레퍼런스

### 7.1 `js/auth.js` — 로그인·교사 승인·QR

- **`getOrCreateVisitorKey()` / `VISITOR_KEY`** — 방문자 고유 키(localStorage). Supabase 클라이언트보다 먼저 만들어야 해서 이 파일 맨 앞에 있음
- **`supabaseClient`** — `global.headers`에 `x-visitor-key`를 실어 생성
- **`SHARE_CODE_FROM_URL`** — 주소의 `?t=` 값
- **`enterWithSession(session)`** — 로그인 세션이 생기면 `teachers`에서 승인 상태 확인. 승인 전/거절이면 로그아웃하고 안내 문구 표시. 승인이면 `currentTeacher` 저장 후 입장. 공유 링크 없이 들어왔는데 로그인 전에 불러온 전시가 내 기준이 아니면 한 번 새로고침
- **`waitForArtworksLoad()`** — 다른 파일의 `window.artworksLoadPromise`가 끝날 때까지 대기
- **`getShareUrl()` / `renderEntryQR()`** — 교사 로그인 시 내 `share_code`, 공유 링크로 들어온 방문자는 그 코드를 붙인 주소로 QR 생성
- **`showGalleryEntry(asTeacher)`** — 시작 화면 표시, 교사일 때만 관리자·로그아웃 버튼 노출
- 주의: `onAuthStateChange` 콜백 안에서 바로 Supabase를 호출하면 멈출 수 있어 `setTimeout`으로 미룸

### 7.2 `js/gallery-data.js` — 데이터 불러오기

- **`loadArtworksData()`** — 보여줄 전시 결정 순서: ① `?t=코드` → `get_active_exhibition(코드)` ② 교사 세션 → 내 `is_active` 전시 ③ 그 외 → `get_active_exhibition(null)`(관리자의 현재 전시, 기존 QR 호환). 실패하면 데모 전시
- 좋아요 수는 `like_counts()` RPC, 내 좋아요 여부는 `likes`에서 내 `visitor_key` 행만 조회
- **`LOADED_AS_USER`, `OWNS_LOADED_EXHIBITION`, `DEMO_MODE`** — 어떤 기준으로 불러왔는지, 내 전시인지(댓글 숨김 버튼 노출 기준), 데모인지

### 7.3 `js/scene.js` — 3D 전시장

| 상수 | 의미 |
|---|---|
| `LOBBY` | 로비 크기 `{minX:-6,maxX:6,minZ:-1,maxZ:6,h:5}` |
| `CORR_MINX/MAXX`, `CORR_HALF`, `CORR_WIDTH` | 복도·문 폭 (2.8) |
| `CORR_LEN` | 방 사이 복도 길이 (6) |
| `ROOM_H` | 전시실 높이 (5) |
| `ROOM_FRONT_MARGIN`, `ROOM_BACK_MARGIN`, `ARTWORK_STEP` | 작품 배치 간격 |
| `WING_CENTER_A`(-4), `WING_CENTER_B`(4) | A동·B동 복도 중심 x |
| `WING_ROOM_OUT` | 전시실이 바깥쪽으로 뻗는 폭 (10) |
| `DOOR_H` | 문틀 높이 (4.0) |

## 8. 주요 의사결정과 이유

| 결정 | 이유 |
|---|---|
| 로컬 폴더를 지우고 원격을 clone해 작업 | 로컬본이 원격보다 한 커밋(전시장 교체 기능) 뒤처져 있어, 그대로 올리면 배포된 기능이 사라졌음 |
| 회원가입 즉시 교사 → **관리자 승인제** | 가입이 열려 있고 이메일 인증도 생략되어, 학생이 아무 이메일로 가입해 전시 전체를 지울 수 있었음 |
| 전시에 `owner_id`, 교사별 `is_active` 하나 | "다른 교사의 전시는 볼 수 없게" 요구 + 방문자 QR은 교사마다 고정되어야 함 |
| 공유 링크를 교사 코드(`?t=`)로 | 전시 ID로 하면 현재 전시를 바꿀 때마다 QR이 바뀜. 교사 코드면 인쇄한 QR을 계속 사용 가능 |
| 코드 없는 주소는 관리자의 현재 전시로 | 이미 배포·공유된 QR·링크가 깨지지 않도록 하위 호환 |
| 새 전시 업로드 시 자동 공개하지 않음(현재 전시가 없을 때만 자동) | 기존 방식은 업로드 도중 학생 화면이 데모로 바뀌거나 갑자기 다른 전시로 바뀌었음 |
| 정책 헬퍼를 `private` 스키마에 | API(RPC)로 노출되지 않게 해 공격 면을 줄이고 보안 진단 경고도 피함 |
| 좋아요는 요청 헤더 + `like_counts()` | 비로그인 방문자를 서버가 구분할 방법이 없어, 헤더로 받은 키와 행을 비교. 남의 키가 보이지 않게 행 조회는 본인 것만 허용하고 개수는 함수로 집계 |
| 관리자도 다른 교사의 전시는 못 봄 | 교사 간 개인정보 분리 원칙. 관리자 역할은 승인으로 한정 |
| 발표용 테스트 계정은 "복사본" 방식 | 공동 관리 권한은 실수로 원본을 지울 위험. 복사본은 이미지 파일만 공유하고, Storage 정책상 복사본 쪽에서 원본 이미지를 지울 수 없음 |
| 시작 화면을 입장권 한 장으로 | 배경 왼쪽 위에 이미 제목이 그려져 있어 가운데 큰 제목이 겹쳤음. 패널을 PC 오른쪽·모바일 아래로 옮기고, QR 영역을 "뜯는 입장권"으로 표현 |
| 벽 충돌은 "걸을 수 있는 공간 = 세그먼트 합집합" 검사 추가 | 기존 x 제한 로직을 건드리지 않고 덧붙이는 방식이라 회귀 위험이 작고, 전시실 수와 무관하게 동작 |
| 파일 분리는 모듈화 없이 "잘라서 옮기기" | ES 모듈·빌드 도구로 바꾸면 코드 수정이 많아짐. 일반 `<script>` + 같은 순서면 동작이 그대로이고 GitHub Pages 배포 방식도 그대로 |

## 10. 보안·성능 고려사항

- **anon key**는 공개되어도 되는 키이며, 보호는 RLS가 담당합니다(4.4절). Service Role Key는 절대 코드에 넣지 않습니다.
- **Supabase Auth 설정(대시보드)**: 회원가입 허용(승인제가 있으므로 안전), **이메일 인증(Confirm email) 켬**, Google 로그인 꺼짐(앱 버튼도 숨김).
- **보안 진단(advisors) 현황**: `get_active_exhibition`, `like_counts`가 비로그인 실행 가능한 SECURITY DEFINER 함수라는 경고 2건 — 방문자용으로 **의도적으로 공개**한 함수. 유출 비밀번호 차단(Leaked Password Protection) 꺼짐 경고 1건 — 계정 수가 적어 우선순위 낮음.
- **이미지 업로드 제한**: 10MB 이하, jpeg/png/webp/gif만. 업로드·삭제는 내 전시 폴더(`전시ID/…`)에만 가능.
- **성능**: 가까운 방 조명만 씬에 유지, 그림자는 현재 방만, 그림자맵 768. 벽 검사(`isWalkable`)는 프레임당 사각형 약 10개 × 4점 비교로 부담이 거의 없음. 정책 헬퍼는 `stable` 함수이고 `(select auth.uid())` 형태로 호출.

1. 관리자 페이지에서 사진 15장 이상 업로드 → 전시실 3~4개 생성
2. 로비 왼쪽 문으로 들어가 첫 방부터 순서대로 관람, 입장·퇴장이 어디서도 막히지 않는지(특히 연결 통로 앞뒤)
3. 연결 통로를 지나 반대쪽 동 → 로비 오른쪽 문("출구")으로 복귀
4. 로비 환영 사인에 실제 학년/반 표시, 문틀 떨림 없음, 방마다 다른 색 띠
5. 작품 8개 이하(전시실 1개)에서도 정상 동작
6. 시작 화면 QR이 그려지는지, 다른 기기(휴대폰)로 스캔해 같은 전시가 열리는지, "링크 복사"
7. 로비 코브 라이트·메달리온·브라스 라인, 전시실은 차분한 톤 유지
8. 모바일: 조이스틱 표시·이동, 드래그로 시선, 탭으로 작품 확대, 첫 입장 안내 카드
9. 감상 결과 리포트 다운로드 → **인터넷을 끄고** 열어도 이미지·좋아요·댓글·검색·정렬·인쇄 동작
10. **[Phase 7]** 새 계정 가입 → "승인 대기" 안내 후 로그인 화면 유지 → 관리자가 승인 → 다시 로그인하면 관리자 버튼 표시
11. **[Phase 7]** 교사 A로 만든 전시가 교사 B의 "기존 전시 관리" 목록에 보이지 않는지
12. **[Phase 7]** 교사 로그인 시 시작 화면 QR·링크에 `?t=내코드`가 붙는지, 그 링크로 다른 기기에서 내 현재 전시가 열리는지
13. **[Phase 7]** "현재 전시장으로 설정" 후 공유 링크가 그 전시로 바뀌는지, 새 전시 업로드가 기존 현재 전시를 바꾸지 않는지
14. **[Phase 7]** 좋아요 누르기·취소, 새로고침 후에도 내 좋아요 표시 유지
15. **[Phase 7]** 시작 화면·전시장 안 로그아웃 → 로그인 화면으로 복귀
16. **[Phase 7]** 2관 → 연결 통로 → 3관 가운데 벽, 전시실 앞뒤 벽에 부딪히면 멈추고 비스듬히 부딪히면 미끄러지는지
17. **[Phase 7]** 시작 화면을 PC·휴대폰에서 열어 배경 제목이 잘리거나 가려지지 않는지

## 12. 배포

- **방식**: GitHub Pages, Settings → Pages → Deploy from a branch → `main` / `(root)`. push 후 1~2분 안에 자동 반영.
- **주소**: https://poguni.github.io/class-virtual-gallery/ (교사별 링크: `…/?t=교사코드`)
- **배포 전 체크**: CSS/JS를 바꿨다면 `index.html`의 `?v=날짜` 갱신.
- **DB 변경 절차(Phase 7에서 정립)**:
  1. `supabase/migrations/`에 SQL 작성 + `supabase/rollback/`에 되돌리기 SQL 작성
  2. 끝을 `commit` 대신 오류로 끝나게 바꿔 **시험 실행**(역할별 권한 테스트 포함) → 실행 후 아무것도 남지 않았는지 확인
  3. 수업이 없는 시간에 **SQL 적용과 앱 push를 한 번에**(앱과 DB가 서로 의존하는 변경이면 따로 올리면 잠시 깨짐)
  4. 보안 진단 재실행 + 배포 사이트 확인
- **되돌리기**: `supabase/rollback/20261023_teacher_approval_and_ownership_rollback.sql` + 앱은 커밋 `8c4c05f` 이전으로. 단, 그 이후 디자인·버그 수정도 함께 되돌아가므로 필요한 부분만 골라 되돌리는 것을 권장.

## 13. 알려진 한계

- **교사마다 방문자에게 공개되는 전시는 하나**입니다. 한 교사가 여러 반 전시를 동시에 공개할 수 없습니다.
- **현재 전시는 공개용이라**, API를 직접 다루는 사람은 다른 반의 현재 전시 목록을 조회할 수 있습니다(지난 전시는 불가).
- **좋아요 중복 방지는 브라우저 기준**입니다. 다른 브라우저·시크릿 창에서는 다시 누를 수 있고, 키를 지어내 좋아요를 늘릴 수도 있습니다.
- **댓글 부적절어 필터가 없습니다**(사용자 결정으로 보류). 교사가 숨김으로 대응합니다.
- **진열 순서와 정렬을 `created_at`에 의존**합니다. 작품 순서를 바꾸면 `created_at`이 재기록됩니다.
- **JS 파일이 전역 변수를 공유**하므로 불러오는 순서에 의존합니다. 새 파일을 추가할 때 위치를 신중히 정해야 합니다.
- **발표용 테스트 계정의 복사본 전시**는 원본과 이미지 파일을 공유합니다. 복사본에서 작품을 지워도 이미지 파일은 남습니다(원본 보호를 위한 의도된 동작).
- 로그인 후 처음 들어올 때, 로그인 전에 불러온 전시가 내 기준이 아니면 **페이지가 한 번 새로고침**됩니다.
- `favicon.ico`가 없어 콘솔에 404가 하나 남습니다(기능 영향 없음).
